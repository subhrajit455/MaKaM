01 Module Overview

The Notifications Module is the centralized messaging, alerting, and transactional communication hub of the MaqamTravels platform. It handles omnichannel user engagement across travel booking lifecycles, payment states, authentication events, and administrative alerts.

Decoupled Asynchronous Dispatch

Decouples core checkout, booking, and webhook flows from third-party communication latency (SMTP, SendGrid, Twilio, SMS gateways).

Guaranteed Delivery & Idempotency

Implements deduplication keys to guarantee that guests are never spammed or double-billed with duplicate confirmation alerts.

Auditability & Compliance

Persists a transactional audit log (NotificationLog) tracking delivery status, provider message IDs, timestamps, and failure reasons.

Multi-Provider Resilience

Supports primary and fallback transport channels (e.g., SMTP fallback to SendGrid, or international SMS fallbacks).

03 System Architecture & Flow

The notifications engine follows an Asynchronous Outbox / Worker Queue Pattern to ensure API response times remain under 100ms even when external email/SMS providers experience throttling or network latency.

04 Component Specifications

4.1 Notification Data Model (notification.model.js)

The NotificationLog schema stores the complete lifecycle of every communication sent across the platform:

JavaScript / Mongoose modules/notifications/notification.model.js 
const mongoose = require('mongoose');
const { Schema } = mongoose;

const NotificationLogSchema = new Schema(
  {
    userId: {
      type: Schema.Types.ObjectId,
      ref: 'User',
      index: true,
      default: null,
    },
    recipient: {
      email: { type: String, trim: true, lowercase: true },
      phone: { type: String, trim: true },
    },
    channel: {
      type: String,
      enum: ['email', 'sms', 'push', 'in_app'],
      required: true,
      index: true,
    },
    eventType: {
      type: String,
      required: true,
      enum: [
        'booking_confirmation',
        'booking_cancellation',
        'ticket_issued',
        'payment_success',
        'payment_failed',
        'refund_processed',
        'visa_status_updated',
        'otp_verification',
        'password_reset',
        'welcome_user',
        'admin_alert',
      ],
      index: true,
    },
    subject: { type: String, default: '' },
    bodyContent: { type: String, default: '' },
    templateName: { type: String, default: null },
    metadata: { type: Schema.Types.Mixed, default: {} },
    
    status: {
      type: String,
      enum: ['queued', 'processing', 'sent', 'delivered', 'failed', 'bounced'],
      default: 'queued',
      index: true,
    },
    provider: {
      name: { type: String, default: null }, // e.g. 'nodemailer', 'sendgrid', 'twilio'
      messageId: { type: String, default: null },
      response: { type: Schema.Types.Mixed, default: null },
    },
    attempts: { type: Number, default: 0 },
    lastError: { type: String, default: null },
    idempotencyKey: {
      type: String,
      unique: true,
      sparse: true,
      index: true,
    },
  },
  { timestamps: true }
);

module.exports = mongoose.models.NotificationLog || mongoose.model('NotificationLog', NotificationLogSchema);

4.2 Unified Notification Service (notification.service.js)

Acts as the single point of entry for the entire application. Exposes domain-specific helper methods while abstracting channel selection.

JavaScript Interface modules/notifications/notification.service.js 
class NotificationService {
  /**
   * Generic dispatch routing to email/sms workers with deduplication
   */
  async dispatch({ channel, eventType, recipient, subject, template, data, idempotencyKey });

  /**
   * Booking confirmed notification (Sends Email with HTML voucher + SMS confirmation)
   */
  async sendBookingConfirmation(booking, payment);

  /**
   * Payment failure alert
   */
  async sendPaymentFailed(payment, reason);

  /**
   * Refund credited confirmation
   */
  async sendRefundConfirmation(payment, refundData);

  /**
   * Flight e-ticket issued with PNR and attached PDF
   */
  async sendFlightTicketed(booking, ticketDetails);

  /**
   * Visa application status transition alert (Approved / Documents Requested)
   */
  async sendVisaStatusUpdate(application, newStatus);

  /**
   * One-time password (OTP) delivery for mobile authentication
   */
  async sendOtp(phone, otpCode);
}

4.3 Email Sub-service (email/emailService.js)

Specialized for rich HTML emails, branded layouts, and transactional attachments (PDF invoices, vouchers).

1. HTML Templating

Responsive templates designed for desktop and mobile clients (Apple Mail, Gmail, Outlook) with cross-client CSS support.

2. Dynamic Injections

Customer name, PNR numbers, flight itineraries, hotel check-in times, barcode images, and pricing summaries.

3. Attachments

Dynamic generation and streaming of PDF attachments (e.g., flight e-tickets, hotel booking confirmation vouchers).

4. Transport Adapters

Development: Ethereal / Local console transport.
Staging / Production: SMTP (Hostinger / Google Workspace / Amazon SES / SendGrid).

4.4 SMS Sub-service (sms/smsService.js)

Specialized for critical, high-urgency notifications (OTPs, flight gate changes, instant payment confirmations).

1. Regional Phone Normalization

E.164 phone formatting: +91... for India, +966... for Saudi Arabia Umrah pilgrims, +971... for UAE.

2. Length Guardrails

Concise 160-character payloads engineered for single-SMS cost efficiency and instant deliverability.

3. DLT Compliance

Registered template headers and sender IDs conforming strictly to Indian telecom regulations (TRAI DLT).

4. Gateway Adapters

Integrated connectors for Twilio, Fast2SMS, and MSG91 with automatic failover.

07 Queue, Idempotency & Retry Architecture

7.1 Idempotency Key Format

To avoid duplicate emails or SMS messages when webhooks retry or user submits requests twice:

Formula: idempotencyKey = hash(eventType + channel + entityId + status)

Example: booking_confirmation:email:64f8e5d32b1a4c9f12345678:CONFIRMED

7.2 BullMQ Queue Configuration

Queue Parameters

  • Queue Name: notification
  • Concurrency: 5 concurrent job workers
  • Dead Letter Queue (DLQ): notification-dlq (alerts DevOps team upon final failure)

Retry Strategy Timeline

Attempt 1 Immediate

First dispatch triggered right upon message arrival.

Attempt 2 + 30 Seconds

Exponential backoff for temporary socket or rate-limit hiccups.

Attempt 3 + 2 Minutes

Final retry attempt before routing to Dead Letter Queue (DLQ).

09 Developer Implementation Roadmap

When completing the code inside the skeleton files, follow this recommended sequence:

Step 1 — Model Definition (notification.model.js)
Implement NotificationLog Mongoose schema with indexes on idempotencyKey, status, and createdAt.
Step 2 — Email Transport (email/emailService.js)
Initialize Nodemailer transporter with connection pooling. Add responsive HTML wrapper with standard header, footer, and branding.
Step 3 — SMS Transport (sms/smsService.js)
Implement phone number parser and Twilio / Fast2SMS HTTP integration with E.164 normalization.
Step 4 — Unified Orchestrator (notification.service.js)
Implement sendBookingConfirmation, sendPaymentSuccess, and sendOtp. Wire up NotificationLog creation and status updates.
Step 5 — Worker Hookup & Webhooks
Link the service methods into utils/paymentOrchestrator.js and flight.callback.service.js.
