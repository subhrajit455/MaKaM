1. Executive Overview & Design Philosophy

IAM ARCHITECTURE

The OTP Authentication subsystem provides frictionless, passwordless registration and login for consumer travelers on the Maqam Travels platform. It replaces traditional email/password registration with phone number verification compliant with Indian telecommunication (TRAI / DLT) mandates.

Zero Password Fatigue

Travelers log in or register in under 10 seconds with a 10-digit mobile number and instant 6-digit verification code.

Unified Auth Endpoint

Both new account registration and existing traveler login use the identical two endpoints (`/send-otp` & `/verify-otp`).

Cryptographic Burn

Single-use security guarantee: OTP tokens are burned from cache immediately upon first successful use or 5 failures.

TRAI DLT Compliance

Dispatches SMS via registered sender ID MAQAMH and approved message template 224018.

Architectural Boundary: B2C Travelers vs B2B Back-Office

To preserve organizational security, the Maqam Travels platform strictly bifurcates consumer traveler authentication from staff back-office access:

Consumer Public Portal (B2C)
  • Primary Mode: Passwordless Phone OTP
  • Self-Registration: Automatic upon first OTP verification
  • Role Assignment: Strictly enforced as 'customer'
  • Endpoints: /api/v1/auth/send-otp, /verify-otp
Back-Office / CRM / Staff (B2B)
  • OTP Authentication: STRICTLY PROHIBITED
  • Credential Mode: Email/Username + Bcrypt Password
  • Provisioning: Super Admin manual onboarding
  • Roles: 'sales_agent', 'accountant', 'admin'

3. End-to-End System Workflows

SEQUENCE FLOWS

Workflow A: OTP Generation & Dispatch (`/send-otp`)

Initiated when a customer submits their 10-digit phone number in the web app or mobile app:

sequenceDiagram autonumber actor Traveler as 📱 Traveler (App/Web) participant Route as auth.routes.js participant Controller as auth.controller.js participant Service as auth.service.js participant Cache as Redis (utils/cache.js) participant DB as MongoDB (User & OTP) participant SMS as Fast2SMS (DLT Gateway) Traveler->>Route: POST /api/v1/auth/send-otp { phone: "9876543210" } Route->>Controller: sendOtpController(req, res) Controller->>Controller: Normalize phone (trim whitespace) Controller->>DB: User.findOne({ phone: "9876543210" }) alt Account is Deactivated (user.isActive === false) Controller-->>Traveler: 403 Forbidden ("Account is deactivated") else Account Active or New Controller->>Service: sendOtpService(phone) Service->>Service: Validate regex: /^[6-9]\d{9}$/ Service->>Service: Generate crypto OTP: crypto.randomInt(100000, 999999) Service->>Service: Calculate expiresAt = Date.now() + 300,000ms Service->>Cache: cache.set("otp:9876543210", { otp, attempts: 0 }, 300000) Service->>DB: (Fallback) OTP.findOneAndUpdate(...) alt Production Mode (NODE_ENV === 'production') Service->>SMS: sendOtpSMS("9876543210", otp) SMS-->>Service: { return: true, request_id: "..." } else Development Mode Service->>Service: Log to server console [DEV OTP: 482931] end Service-->>Controller: { success: true, phone, expiresInSeconds: 300 } Controller-->>Traveler: 200 OK ("OTP dispatched successfully") end

Workflow B: OTP Verification & Auto-Provisioning (`/verify-otp`)

Validates code, enforces retry counters, auto-registers new users, and issues dual tokens:

sequenceDiagram autonumber actor Traveler as 📱 Traveler (App/Web) participant Controller as auth.controller.js participant Service as auth.service.js participant Cache as Redis (utils/cache.js) participant DB as MongoDB (User & OTP) participant Token as JWT Engine Traveler->>Controller: POST /api/v1/auth/verify-otp { phone: "9876543210", otp: "482931" } Controller->>Service: verifyOtpService(phone, otp) Service->>Cache: cache.get("otp:9876543210") alt Missing in Redis Service->>DB: OTP.findOne({ phone: "9876543210" }) end alt No Record or Already Expired Service-->>Controller: Error ("OTP not found or expired") Controller-->>Traveler: 400 Bad Request else Record Active alt Wrong OTP (Mismatch) Service->>Service: attempts = attempts + 1 alt attempts >= 5 (Max Exceeded) Service->>Cache: cache.del("otp:9876543210") (BURN) Service->>DB: OTP.deleteOne({ phone }) Service-->>Traveler: 400 Bad Request ("Max attempts exceeded. Request new OTP.") else attempts < 5 Service->>Cache: Update remaining attempts in Redis Service-->>Traveler: 400 Bad Request ("Invalid OTP. 4 attempts remaining.") end else Correct OTP (Match!) Service->>Cache: cache.del("otp:9876543210") (SINGLE-USE BURN) Service->>DB: OTP.deleteOne({ phone }) Service->>DB: User.findOne({ phone }) alt User Already Exists Service->>DB: user.isPhoneVerified = true, user.lastLogin = Date.now() else New Traveler Service->>DB: User.create({ phone, role: 'customer', randomBcryptPassword }) end Service->>Token: generateTokens(user._id, user.role) Token-->>Service: { accessToken (120m), refreshToken (7d) } Service-->>Controller: { user, accessToken, refreshToken } Controller->>Controller: Set-Cookie: refreshToken (HttpOnly, Secure) Controller-->>Traveler: 200 OK (User Profile + Access Token) end end

Workflow C: Session Management & Refresh Token Flow

Maintains persistent authentication without requiring repeated OTP entries:

1. Access Token

Lifespan: 120 minutes. Transmitted in Authorization: Bearer <token> header for stateless API validation.

2. Refresh Cookie

Lifespan: 7 days. Stored in HttpOnly, Secure, SameSite=None cookie to eliminate XSS token theft.

3. Transparent Renewal

When API returns 401, frontend calls POST /refresh-token to receive a fresh access token without user friction.

7. Telecom & TRAI DLT Regulatory Gateway (Fast2SMS)

REGULATORY COMPLIANCE

Under Telecom Regulatory Authority of India (TRAI) directives, bulk transactional SMS must be dispatched through registered Distributed Ledger Technology (DLT) entities. Maqam Travels integrates directly with Fast2SMS Bulk V2:

DLT Parameter Configuration / Value TRAI Regulatory Purpose
API Endpoint https://www.fast2sms.com/dev/bulkV2 Fast2SMS Bulk SMS V2 API endpoint
Auth Header authorization: process.env.FAST2SMS_API_KEY Merchant authentication token
Route dlt Mandates strict DLT registry compliance
Sender ID (Header) MAQAMH (FAST2SMS_SENDER_ID) Registered 6-letter enterprise header for Maqam Travels
Template ID 224018 (FAST2SMS_OTP_TEMPLATE_ID) TRAI pre-approved transactional message body template
Template Variable {#var#} → 6-digit numeric OTP Dynamic variable replacement for security code

Non-Production Safe Guard: In development and staging environments, if FAST2SMS_API_KEY is missing or gateway rejects the call, the system transparently logs the OTP to stdout console and succeeds, preventing test suites from hanging.

8. Security Controls & Attack Matrix

CYBER DEFENSE
Threat Vector Risk Mitigation Mechanism Technical Implementation
Brute-Force Guessing High Max 5 Failed Attempts Limit Redis key tracks attempts. On the 5th failure, OTP is deleted instantly from Redis and MongoDB.
Replay Attacks High Single-Use Cryptographic Burning Immediately after code match, cache.del() and OTP.deleteOne() run before JWT token creation.
Predictable OTP High CSPRNG Entropy Uses Node.js native crypto.randomInt(100000, 999999), avoiding pseudo-random Math.random().
Stale Token Reuse Medium Strict Millisecond TTL Redis PX 300000 auto-expiration + manual service timestamp check against expiresAt.
Deactivated Account Bypass Medium Pre-dispatch User State Validation /send-otp queries MongoDB User record; if isActive: false, returns 403 Forbidden.
Token Theft via XSS Medium HttpOnly Cookie Transport Refresh token is delivered via HttpOnly, Secure, SameSite=None cookie inaccessible to browser scripts.
Staff Privilege Escalation High Strict Role Hardcoding OTP auto-registration strictly hardcodes role: 'customer'. Admin/staff roles cannot be obtained via OTP.

12. Production Readiness Checklist

VERIFICATION

Interactive verification checklist. Progress is automatically persisted in your local browser storage:

CSPRNG Randomness: OTP is generated using crypto.randomInt(100000, 999999).
Primary Cache Tier: Redis key otp:{phone} is stored with PX 300000 (5-minute TTL).
Resilient Fallback: MongoDB OTP model has native TTL index { expiresAt: 1 }, { expireAfterSeconds: 0 }.
Brute-Force Guardrail: Maximum 5 wrong verification attempts before automatic cache burning.
Single-Use Burn: Verified OTP is deleted immediately from cache before JWT generation.
Auto-Provisioning: New travelers are auto-registered with role: 'customer' and random Bcrypt hash.
HttpOnly Transport: Long-lived refresh token is transmitted strictly in an HttpOnly, Secure cookie.
DLT Compliance: Fast2SMS uses registered sender ID MAQAMH and DLT template 224018.
