Where Access Tokens & Refresh Tokens Are Stored

To prevent XSS token harvesting while maintaining sub-millisecond API response times, tokens use dedicated storage layers:

Access Token (120m)

  • Client-Side: In-Memory (JavaScript State / React Context / Pinia). Never stored in localStorage (shields from XSS).
  • Transport: Attached via HTTP Header: Authorization: Bearer <token>.
  • Server-Side: Purely Stateless. Not saved in MongoDB. Verified mathematically in-memory using HMAC-SHA256 secret.

Refresh Token (7 Days)

  • Client-Side: HttpOnly, Secure, SameSite=none browser cookie. JavaScript cannot read it via XSS.
  • Transport: Automatically attached by the browser exclusively to /refresh-token and /logout.
  • Server-Side: Persisted in MongoDB RefreshToken collection with native 7-day TTL index. Burned upon use.

Previous vs. Present Workflow Comparison

Security Vector Previous (Legacy Flawed State) Present (Current Production Implementation)
Token Invalidation ❌ Never invalidated (Tokens lived for 7 full days after rotation). 🟢 Single-use burn (Old token is deleted from MongoDB on every refresh).
Replay Attack Detection ❌ Absent (Attacker could replay old token thousands of times). 🟢 Protected (Replay of burned token throws immediate HTTP 401).
Token Uniqueness ⚠️ Deterministic (Risk of token collision in the same second). 🟢 Cryptographic UUID (jwtid: crypto.randomUUID() on every issuance).
Cookie Synchronization ❌ Broken (res.cookie omitted; client stuck on old token). 🟢 Synchronized (New token cookie is refreshed on every rotation).
Logout Revocation ❌ Client-only log (Server kept token active). 🟢 Database Purge (Token deleted from MongoDB on logout).
Password Reset Action ❌ No token cleanup. 🟢 Cascade Purge (Revokes all active refresh tokens for the user).

Present Implementation Deep-Dive

Single-Use Burning Workflow: Every call to POST /api/v1/auth/refresh-token performs an atomic token swap in MongoDB.
  1. Step 1: Client passes refresh token via req.cookies.refreshToken.
  2. Step 2: Server verifies cryptographic signature using REFRESH_TOKEN_SECRET.
  3. Step 3: Server queries MongoDB RefreshToken.findOne({ token }). If not found, immediately raises 401 Unauthorized (Replay Attack!).
  4. Step 4: Server burns the old token: RefreshToken.deleteOne({ _id: tokenDoc._id }).
  5. Step 5: Server checks user status (user.isActive).
  6. Step 6: Server mints brand-new access token + unique refresh token.
  7. Step 7: Server saves new refresh token in MongoDB.
  8. Step 8: Server synchronizes browser cookie: res.cookie("refreshToken", newRefreshToken, options).

Future Implementations & Token Roadmap

1. Redis In-Memory Caching (Sub-Millisecond Verification)

Add a high-speed Redis caching tier (rt:token:<tokenId>) to verify token status in memory, eliminating MongoDB disk reads on high traffic spikes.

2. Token Family Lineage & Automatic Theft Isolation (RFC 6749)

Track session lineage using a permanent familyId. If an attacker replays a burned token, the server detects the breach and revokes all descendant tokens in that family, forcing both attacker and victim to log in again.

3. Multi-Tab Concurrency Grace Window

Provide a 30-second concurrency grace period (graceExpiresAt). If multiple tabs fire simultaneous refresh requests, the server safely re-serves the already-minted child token without triggering a security alarm.

4. Device Fingerprinting & Geographic Anomaly Detection

Bind refresh tokens to client IP subnets and User-Agent fingerprints. Trigger step-up OTP authentication if a token suddenly hops geographical regions.

5. Multi-Device Management Dashboard

Enable travelers to view and terminate active sessions ("Chrome on Windows - Delhi", "iPhone App - Dubai") from their profile settings.
