Architecture & Reliability Specification

Payment Gateway & Lifecycle Architecture

A comprehensive guide to multi-gateway payments (Razorpay, PayPal, Bank Transfer), transactional consistency, distributed locking, idempotency safeguards, and dual-confirmation flows across Maqam Travels.

🏛️ 1. Core Architecture Overview

The Payment Subsystem is engineered as a decoupled, multi-tenant payment broker. It shields specific domain modules (Packages, Offers, Flights, Hotels, Visas) from gateway-specific SDK idiosyncrasies while guaranteeing zero double-charging, at-least-once confirmation, and complete financial auditability.

⚡ Unified Broker

Single abstraction layer for Razorpay, PayPal, and offline wire/bank transfers with standard state transitions.

🛡️ Idempotency & Locks

Anti-tamper SHA-256 payload hashing and MongoDB TTL distributed locks prevent duplicate captures and race conditions.

📋 Dual Synchronization

Synchronous client-side redirect verification and asynchronous webhooks converge seamlessly in bookingSync.js.

💡 Why Two Booking Layers? (Particular Booking vs Master Booking)
Particular Booking (e.g. PackageBooking): Contains domain-heavy state: specific flight seat and hotel room unit allocations, swapped components, traveler passport scans, and linked visa applications.
Master Booking (Booking Model): An ultra-fast, normalized itinerary ledger powering the Customer Dashboard and global CRM search. It is created automatically upon successful payment.

🛡️ 4. Core Resiliency & Security Pillars

4.1 Request Idempotency Engine (idempotency.middleware.js)

Network drops, duplicate button clicks, or mobile reconnects can trigger duplicate HTTP requests. The idempotency engine ensures an operation is executed exactly once regardless of how many times it is submitted.

🔑 How the Idempotency Engine Operates:
  • Client Header: The client supplies an Idempotency-Key header (e.g. UUID v4) with mutation requests.
  • SHA-256 Anti-Tamper Check: The middleware computes crypto.createHash('sha256').update(req.body).digest('hex'). If the same key is reused with a modified request body, the server rejects it with 409 Conflict.
  • Response Interception & Caching: When the operation executes, res.json is intercepted. Successful responses (2xx) and client validation errors (4xx) are cached in MongoDB for 24 hours.
  • Transient Error Safety (No 5xx Caching): If the server encounters a transient database timeout or 500 error, it is deliberately NOT cached, allowing the client to safely retry.

4.2 Distributed Locking (distributedLock.js)

When a customer completes payment, two events happen almost simultaneously: the browser submits a /verify request while the gateway fires an asynchronous payment.captured webhook. Without synchronization, both could run concurrently, leading to race conditions or duplicate ticketing calls.

🔒 Distributed Lock Mechanics:
  • Atomic Acquisition: Employs MongoDB atomic findOneAndUpdate with a unique compound index on resource (e.g. capture:order_xyz987).
  • Re-entrancy & Expiry: Each lock contains { resource, owner, expiresAt }. If a node crashes mid-flight, a MongoDB TTL index automatically evicts the lock after 15 seconds.
  • Graceful Backoff: Competing requests wait with exponential jitter backoff before retrying lock acquisition.

4.3 Webhook Deduplication & Security (webhookEvent.model.js)

🛡️ Signature Verification

Every inbound webhook is verified before inspection. Razorpay webhooks validate the X-Razorpay-Signature using HMAC-SHA256 with the webhook secret. PayPal webhooks verify CRC32/RSA signatures against PayPal public certificates.

📦 At-Least-Once Deduplication

Payment gateways guarantee at-least-once delivery and frequently re-transmit webhooks. Inbound events are atomically logged in WebhookEvent with a unique index on eventId. Duplicates are immediately acknowledged with HTTP 200 and discarded.

4.4 Immutable Audit Logging (auditLog.service.js)

For PCI-DSS compliance and financial accountability, every payment state transition, gateway call, and admin refund is permanently recorded in AuditLog.

🔍 Automated PCI Sensitive Data Redaction:

Before any request or response payload is written to the audit database, the redactSensitiveData recursive scrubber automatically strips and masks credit card numbers, CVVs, passwords, secret keys, and bearer tokens:

// Sanitization Rule Pattern in auditLog.service.js:
const sensitiveKeys = ['password', 'token', 'secret', 'key', 'cvv', 'cvc', 'cardnumber', 'pan', 'pin', 'authorization'];
// Any matching field is replaced with: "[REDACTED_SENSITIVE_DATA]"

Non-Blocking Guarantee: Audit logging wraps operations in try/catch blocks that never bubble errors upward, ensuring an audit storage glitch never disrupts customer checkouts.

🎯 Key Takeaways for Developers & Frontend Engineers
  1. Always send Idempotency-Key: The frontend should generate a unique UUID v4 whenever requesting payment order creation or capture.
  2. Trust the Backend Webhook: Even if the user closes their browser tab right after entering their bank OTP, the background webhook will reliably finalize the booking and send confirmation emails.
  3. Inventory Sits with Domain: Stock reservations (holding/releasing) are handled atomically by stockClaim.service.js under the supervision of bookingSync.js.
