Hierarchy Level Core Entities Why It Must Be Created First
Step 1: Wholesale Stock TicketStock, HotelStock Establishes physical baseline capacity and cost price. Individual seat/room units are provisioned with available state.
Step 2: Retail Offers Offer (flight/hotel) Assigns retail selling prices, inclusions, and marketing copy referencing Tier 1 stock. Can be sold standalone or used as package components.
Step 3: Curated Packages Package Curated composite bundles referencing ≥ 2 Tier-2 Offer components. Applies bundle discount percentages and swappable alternative matrices.
Step 4: Bookings & Operations PackageBooking, OfferBooking Reserves physical Tier-1 units atomically (online 30-min hold vs CRM direct 'used' lock), creates master bookings, and handles ops fulfillment.

2. Stock Unit Lifecycle State Machine

Physical inventory units (airline seats and hotel rooms) transition through three strict states to guarantee zero double-booking and automatic stock replenishment on expiration or cancellation.

stateDiagram-v2 [*] --> available: Stock Batch Created (Admin / Hotelier Approved) available --> held: Online Booking Created (Customer POST /packages/book) available --> used: Direct Offline Booking (CRM Agent POST /book-for-customer) held --> used: Payment Verified (Razorpay/PayPal Webhook) held --> available: 30-Min Expiration Worker OR Customer Cancellation used --> available: Admin/Customer Booking Cancelled (Refund & Stock Release) used --> [*]: Travel Completed

3. Option A Pricing Math Explained

Under Option A, the bundle discount is locked onto the default bundle. When users customize, additions and removals happen at standalone retail face-value.

The Golden Formula:
Final Customized Price = Base Package Sell Price - Total Deductions (Opt-outs) + Total Deltas (Swaps)
Guardrail Rule (Minimum 2 Components):
A package must maintain at least 2 active items at all times. If a user unchecks items until only 1 remains, the customizer rejects the request with HTTP 400.

Appends timestamped operational remarks to the booking dossier.

Architectural Evaluation

Is the Current Module a "Perfect Adapter" for Services like Insurance or Tour Guides?

Verdict: Not Yet a Universal Adapter. The current architecture is well-designed for Flights and Hotels, but exhibits coupling that would require code refactoring to cleanly support Insurance, Tour Guides, or Car Transfers.

⚡ Current Architecture Status

  • Uniform Offer Packaging: Visas have been decoupled into standalone products. Package.model.js now bundles offerRefs only. Packages act as pure Offer containers.
  • Hardcoded itemType in Offers: Offer.model.js currently accepts enum: ['flight', 'hotel'] with pre-save hooks for flightRef / hotelRef.
  • Inventory Claim Engine: stockClaim.service.js is pre-configured with TicketStock and HotelStock.

✅ Guide & Insurance Integration Path

  • Expand Offer itemType: Add 'guide' and 'insurance' to the Offer schema with guideRef and insuranceRef.
  • Register in STOCK_MODELS: Add GuideStock and InsuranceStock into stockClaim.service.js. The atomic unit lock engine works out of the box.
  • Zero Package UI Changes: Because Packages bundle Offers generically, Guide and Insurance offers will appear in the Package Builder dropdown with zero Package schema or UI rewrites!
