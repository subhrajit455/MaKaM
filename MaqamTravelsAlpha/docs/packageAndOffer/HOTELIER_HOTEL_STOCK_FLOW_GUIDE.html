Architecture & API Flow Specification

Hotelier & HotelStock Lifecycle Guide

How external hotel partners manage contracted room inventory (HotelStock), the review-gated admin approval queue, and how approved batches plug into live Packages & Offers.

1. The Two Distinct "Hotel" Domains in the System

To prevent confusion, understand that this platform operates two independent hotel subsystems that serve different business models:

Domain A: Live OTA Engine

SRDV Live Hotel Booking

Dynamic third-party API integration. Live price, live availability, instant booking API calls for retail customers searching individual hotels worldwide.

  • Service: hotel-search.service.js, hotel-booking.service.js
  • Model: hotel.model.js (stores HotelBooking)
  • Catalog: hotelCity.model.js (~139k cities)
  • Actor: Public Retail Customer
Domain B: Wholesale & Packages

Partner Hotelier & HotelStock

Direct contracted wholesale room blocks negotiated with specific partner hotels. Bundled into holiday packages and flash offers or managed via self-service.

  • Service: hotelier.service.js, crm.service.js
  • Stock Model: hotelStock.model.js
  • Partner Hotel: hotelEntity.model.js (name, destination, address, isActive)
  • Actor: Partner Hotelier & Agency Admin

3. Hotelier Capabilities (According to Current Code)

The hotelier is authenticated via JWT with role: "hotelier" and bound to a specific hotelId. All operations are strictly confined to batches where stock.hotelId === req.user.hotelId.

Action HTTP Route Payload Example Effect on reviewStatus
List Own Inventory GET /api/v1/hotelier/stock None Read Only (sanitized units)
Create New Batch POST /api/v1/hotelier/stock { destination, roomType, checkIn, checkOut, pricePerNight, meals, reservationRef, nameAdditionDeadline, unitCount: 10 } pending_review (New batch created)
Edit Rate or Dates PATCH /api/v1/hotelier/stock/:id { pricePerNight: 4500, checkIn: "2026-11-01" } Resets to pending_review (Admin must re-approve)
Add Units to Batch POST /api/v1/hotelier/stock/:id/units { count: 5 } Resets to pending_review (Admin must re-approve)
Toggle Room Hold PATCH /api/v1/hotelier/stock/:id/units/:unitId { status: "available" | "blocked" } No Change (Instant toggle for maintenance)

Strict Guardrails & Security Boundaries

  • No Direct Approval: Hoteliers can never modify reviewStatus, reviewedBy, or reviewNotes.
  • No Booking Tampering: Hoteliers can never change unit status to assigned or used. Those statuses are reserved for the checkout booking engine.
  • No Locked Unit Overwrite: Hoteliers cannot change the status of an already assigned or used room unit.
  • PII & Cost Masking: sanitizeStockForHotelier() hides all guest names, passenger lists, booking IDs, and agency pricing markups. Unit status is mapped to available, blocked, or unavailable.

4. Agency Admin CRM Review Bridge

Stock created or edited by hoteliers does not reach the public storefront until an Admin or Super Admin approves it via CRM routes.

Endpoint Role Required Purpose
GET /api/v1/crm/hotel-stock/pending Admin / Super Admin Review queue of all hotelier submissions awaiting action. Populates hotel details.
PATCH /api/v1/crm/hotel-stock/:id/review Admin / Super Admin Body: { decision: "approved" | "rejected", reviewNotes: "..." }
GET /api/v1/crm/hotel-stock/approved Admin / Super Admin Catalog of ready-to-sell batches used by Package / Offer builder dropdowns.

5. How HotelStock Connects with Packages, Offers & Availability

1. Dynamic Live Availability Calculation

Implemented in availability.service.js. Stock availability is never statically cached. It is computed live on read using: 

function isStockUsable(stockDoc) {
  if (!stockDoc) return false;
  // 1. Must be approved by Admin
  if (stockDoc.reviewStatus !== "approved") return false;
  // 2. Hotel property must be active
  if (stockDoc.hotelId && stockDoc.hotelId.isActive === false) return false;
  return true;
}

If an admin deactivates a hotel (isActive: false), all its packages and offers immediately show as 0 seats available without needing a database update job.

2. Atomic Claim at Checkout

Implemented in stockClaim.service.js. When a customer confirms payment: 

const query = { 
  _id: stockId, 
  "units.status": "available", 
  reviewStatus: "approved" 
};
// Atomically sets units.$.status = "assigned"
// Links assignedToBooking = bookingId

If the hotelier edited the batch while the customer was browsing, reviewStatus became pending_review and the checkout claim safely fails with an error rather than overselling.

6. Potential Mistakes, Clutter & Code Observations to Review

Here are the exact architectural gaps, quirks, and potential bugs identified directly in the current implementation:

⚠️
1. Model Collision Danger: hotelInventory.model.js

Inside server/modules/hotels/hotelInventory.model.js, line 49 executes: mongoose.model('Hotel', hotelInventorySchema). Meanwhile, hotelEntity.model.js also defines mongoose.model('Hotel', hotelSchema). If hotelInventory.model.js is ever required before hotelEntity.model.js, Mongoose will throw an OverwriteModelError. Since hotelInventory.model.js is completely unused, it is orphaned dead code and should be deleted.

⚡
2. Misplaced Domain File: hotelEntity.model.js

hotelEntity.model.js (which defines partner hotel profiles like contract notes, tie-up dates, contact person) is located inside server/modules/hotels/ alongside SRDV live OTA code. It has zero relation to SRDV and is exclusively used by modules/hotelier/, modules/crm/, and modules/packages/stock/. It should logically live under modules/hotelier/hotel.model.js or modules/packages/stock/.

✔
3. Rejection & Resubmission Workflow (Confirmed Standard Flow)

If an admin rejects a batch with feedback (e.g. "Rate too high, please reduce to ₹4,000" or "Fix date typo"), the hotelier can edit the batch. The code resets reviewStatus = 'pending_review' and sends it back to the admin queue. This avoids forcing hoteliers to re-type batches from scratch for simple fixes.

🛡️
4. Active Booking Protection (Guard 1 Implemented)

In hotelier.service.js, if any room unit in a batch is already booked by a customer (status === 'assigned' or 'used'), hoteliers are strictly blocked from changing dates (checkIn, checkOut), destination, or roomType. Attempting to do so returns an immediate 400 Bad Request, protecting active customer reservations from date corruption.

How Frontend Implements "Add Room / Hotel Stock"

To create a room allotment in the CRM, the frontend must pass a valid hotelId. Here is the exact recommended workflow:

  1. Fetch Hotels on Page Load: Send GET /api/v1/crm/hotels to populate the Hotel dropdown (e.g. <option value="hotel._id">hotel.name (hotel.destination)</option>).
  2. Submit Room Allotment: Send POST /api/v1/crm/stocks/hotels with: 
    {
  "hotelId": "6aaa35d9d1cad56b320149b5",
  "roomType": "Royal Sky Suite",
  "checkIn": "2026-11-20T00:00:00.000Z",
  "checkOut": "2026-11-25T00:00:00.000Z",
  "pricePerNight": 5500,
  "meals": ["breakfast", "dinner"],
  "reservationRef": "ATL-ROYAL-BLK-01",
  "nameAdditionDeadline": "2026-11-15T00:00:00.000Z",
  "totalUnits": 10
}
  3. If Hotel Doesn't Exist: Open modal to POST /api/v1/crm/hotels (name, destination, address, contactPerson, contactPhone, contactEmail, etc.). On success, automatically select the returned _id in the dropdown.
